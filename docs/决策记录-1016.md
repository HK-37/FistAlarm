## 决策 1:目标形态

- **当时的问题**:用什么技术做?"exe 还是别的方案"。
- **否掉的方案**:① Electron 一把梭——体积 150MB+、常驻内存 150-300MB;② 纯 Python(Qt/pygame)画碎裂——效果上限低;③ 不做托盘只做定时任务拉起的单次播放器——用户明确要管理界面。
- **结论**:Python + pywebview,一个 exe 靠启动参数区分「托盘常驻」与「`--strike` 动画播放」。
- **理由**:**用户判断**(逐项选定:要管理界面 → 拆两截 → 碎后显示提醒文字 → Python+WebView2)。
- **代价与可逆性**:WebView2 缺失时要提示安装(Win11 自带)。换壳代价大,但换壳本身无必要。
- **实现位置**:`fistalarm/__main__.py`、`fistalarm/strike_player.py`

## 决策 2:"击碎屏幕"不用透明窗口

- **当时的问题**:怎么做出"屏幕被打碎"的观感?
- **否掉的方案**:真做多窗口 + 桌面透明合成——要把桌面图标、其他窗口都当作可交互的碎片,不可行。
- **结论**:触发时**先截一张桌面图**,用无边框全屏置顶窗口显示这张图,然后在图上播碎裂动画。
- **理由**:**AI 判断**(这是此类桌面整蛊效果的常规做法)。
- **代价与可逆性**:截图必须发生在开窗口之前,否则截到自己的窗口。截图失败时降级纯黑背景。可逆。
- **实现位置**:`fistalarm/runner.py` 函数 `_fire`、`fistalarm/capture.py`

## 决策 3:测试边界

- **当时的问题**:哪些该写测试?
- **否掉的方案**:给动画写断言——Canvas 渲染结果无法用断言表达,只会写出脆弱的假测试。
- **结论**:逻辑层 98 个用例(时间计算、持久化、编排);动画靠 `--test` 人工看。
- **理由**:**AI 判断**。
- **代价与可逆性**:**动画的视觉正确性没有自动化保障**,只能靠人眼。这是有意的取舍,不是疏漏;README 与 CLAUDE.md 都写明了"退出码 0 说明不了画面"。
- **实现位置**:`tests/`(3 个测试文件)

## 决策 4:副作用注入

- **当时的问题**:调度逻辑要怎么测——它要截屏、要起进程、要读时钟?
- **否掉的方案**:在 runner 里直接调 `mss` / `subprocess`,测试时 monkeypatch 模块函数。
- **结论**:定义 `RunnerHooks`(截屏/播放/时钟/sleep 四个可注入函数),默认真实实现。
- **理由**:**AI 判断**(monkeypatch 打补丁容易随重构失效;显式注入一眼看懂依赖边界)。
- **代价与可逆性**:构造函数多一层。可逆。
- **实现位置**:`fistalarm/runner.py` 类 `RunnerHooks`

## 决策 5:重复触发防护

- **当时的问题**:测试发现同一分钟内连调 3 次 tick 会触发 3 次。
- **否掉的方案**:只靠 grace 窗口防重——用户秒关窗口时窗口还没过去,tick 会再判一次 due。
- **结论**:额外记录每条闹钟"最近一次已处理的触发时刻"(`self._handled`),同一个触发点只处理一次;换了触发点(贪睡到点、下一天)则放行。
- **理由**:**AI 判断**(由测试失败暴露,非预设)。
- **代价与可逆性**:多一份内存状态;进程重启后 `_handled` 清空,理论上重启瞬间可能补响一次已处理过的闹钟——实际影响很小(重启通常发生在触发之后很久)。可逆。
- **实现位置**:`fistalarm/runner.py` 函数 `tick_once`

## 决策 6:播放器与托盘的通信方式

- **当时的问题**:播放器怎么把"用户点了贪睡"告诉托盘端?
- **否掉的方案**:① socket/本地 HTTP——需要端口管理、可能被防火墙拦;② 写临时文件——要考虑清理和并发。
- **结论**:用**进程退出码**:`0` = 关闭,`2` = 贪睡,其他 = 异常(按关闭处理并记日志)。
- **理由**:**AI 判断**。
- **代价与可逆性**:语义容量小(只能表达这几种),但目前够用;崩溃退出码(如 137)与"关闭"要区分开,已在 `StrikeResult` 里处理。可逆。
- **实现位置**:`fistalarm/player.py`、`fistalarm/strike_player.py`

## 决策 7:贪睡的语义

- **当时的问题**:贪睡该改重复规则,还是只延后这一次?
- **否掉的方案**:把贪睡实现成"修改 time 字段再改回来"——会污染用户配置,且改回时机难处理。
- **结论**:独立的 `snooze_until` 字段(一个绝对时刻)。设置了就优先于重复规则;触发后清空。
- **理由**:**AI 判断**。
- **代价与可逆性**:单次闹钟贪睡时不能立即禁用(要等真的响过),已在 `is_expired` 里处理。可逆。
- **实现位置**:`fistalarm/schedule.py` 函数 `snooze` / `clear_snooze`
